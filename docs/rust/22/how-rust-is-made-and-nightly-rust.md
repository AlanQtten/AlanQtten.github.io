# 附录F：Rust的诞生和“Nightly Rust”

本节附录是关于Rust的诞生，以及它对你作为一个Rust开发者的影响的。

## 稳定而不停滞

作为一门语言，Rust对代码的稳定性*十分*关注。我们希望Rust为你打造的内容提供了坚实的基础，而如果语言本身不停地变化，这一点就是无稽之谈。同时，如果我们不对新的特性进行实验，那么我们可能会在发布后才意识到一些重大的缺陷，但那时再做改变就为时已晚了。

这个问题的解法就是“稳定而不停止”，我们的原则是：你永远不应该对升级新版本的Rust感到恐惧。每一次升级都是无痛的，但它们都能引入新的功能，少量的漏洞而更短的编译时间。

## 呜——呜——🚂！发布的火车来喽

Rust的开发遵循*火车时间表*。具体来说，所有的开发都在Rust仓库的`master`分支上完成。发布遵循软件发布的火车模型，Cisco IOS和其他很多软件项目都使用它来发布。Rust的*发布通道*有三个：

- Nightly
- Beta
- Stable

大部分Rust开发者主要使用的是stable的通道，但那些希望尝鲜的人可以使用nightly或beta版本。

下面是一个关于开发和发布流程的例子：假设现在Rust团队在开发Rust1.5版本。这次发布会在2015年的12月，但实际的版本号已提前放出。Rust添加了一个新特性：一个新的提交被合并到了`master`分支上。每天晚上，一个新的nightly版本都会发布。每一天都是发布日，这些发布由我们的基础设施自动提供。随着时间的推移，我们一夜一次的构建如下：

```
nightly: * - - * - - * 
```

每六周，就是发布新版本的时候了！一个`beta`分支从Rust仓库的`master`分支被创建。现在，有两个发布版本：

```
nightly: * - - * - - *
                     |
beta:                *
```

大部分Rust用户不会在生产环境里使用beta版本，但它们的CI系统可以基于beta版本运行测试，来协助Rust发现潜在的问题。同时，nightly版本仍然会保持发布：

```
nightly: * - - * - - * - - * - - *
                     |
beta:                *
```

假设一个回归问题被发现了。好在我们仍然有时间来对beta版本进行测试，避免这个问题卡在稳定版本里！这个修复被提交到了`master`，所以nightly版本的Rust被修复了，然后这个修复会被反向移植到`beta`分支，一个新的beta版本诞生了：

```
nightly: * - - * - - * - - * - - * - - *
                     |
beta:                * - - - - - - - - *
```

在第一个beta版本发布后又过了六周，是时候发布稳定版本了！我们会从`beta`分支检出`stable`分支：

```
nightly: * - - * - - * - - * - - * - - * - * - *
                     |
beta:                * - - - - - - - - *
                                       |
stable:                                *
```

万岁！Rust1.5完成了！然而，我们忘记了一件重要的事：由于已经过去了六周，此时我们还需要发布*下一个*版本的Rust，1.6，也就是说，在从`beta`分支切换出`stable`分支后，我们需要再从`nightly`创建新的`beta`分支：

```
nightly: * - - * - - * - - * - - * - - * - * - *
                     |                         |
beta:                * - - - - - - - - *       *
                                       |
stable:                                *
```

这种模式之所以被称为“火车模型”，就是因为每过去六周，一个版本会“离开车站”，但beta需要一段时间才能到达稳定版本。

Rust的发布就像上了发条一样，每六周一次。如果你知道了一个Rust的发布日期，你就可以知道下一个日期：六周后。从一个有趣的角度看的话，就像是等待一个六周后会按时到达的火车。如果一个特性错过了一次特定的发布，也不需要担心：很快下一班车就会到达！这样的特性有助于减少一些未经打磨的特性为了赶上发布的截止日期而偷偷摸摸地推出。

感谢这个流程，你可以永远切换到下一个Rust的构建，然后自行检查升级后的效果：如果一个beta版本并没有和预期一致，你可以向团队报告，让它在下一个稳定版本中得到修复！beta版本的漏洞很少见，但`rustc`毕竟是一个软件，漏洞是客观存在的。

## 维护时间

Rust项目会维护最近的一个稳定版本。当一个新的稳定版本被发布后，老的版本就进入了生命结束周期（end of life, EOL）。也就是说每一个版本会维护六周。

## 不稳定的特性

这个发布模型还有一个问题：不稳定的特性。Rust使用一种叫做“特性标记（feature flags）”的技术来决定在发布中哪些特性被启用了。如果一个新的特性在积极的开发中，并在`master`进行落地，也就是nightly版本，它会隐藏在一个*特性标记*后。如果你作为用户，希望尝试一个还处于WIP（work-in-progress）的功能，那么你可以使用nightly版本的Rust，然后使用对应的标记来将新特性引入你的源码。

如果你在使用一个beta或者稳定版本的Rust，你就无法使用任何的特性标记了。这是关键所在，它使我们能够在将新功能永久标为稳定之前，先进行实际使用。那些希望体验最前沿技术的人可以采用前面的办法，而那些希望让自己的代码坚不可摧的人可以保持使用稳定版本，并清晰地明白他们的代码不会有问题。稳定而不停滞。

本书只包含了稳定特性的功能，由于一些开发中的特性还在变动，它们很可能会在发布到稳定版本时和本书出现不一致的情况。你可以查看仅在nightly版本中可用特性相关的文档来了解它们。

## `rustup`和nightly Rust的角色

rustup使得在不同的Rust版本之间切换变得非常容易，不管是全局还是项目维度。默认来说，你使用的是稳定版本的Rust。要安装nightly版本的话，可以使用如下代码：

```bash
$ rustup toolchain install nightly
```

你可以查看所有使用`rustup`安装的*工具链*（Rust及其关联组件的发布）。下面是在一台windows电脑上查看的：

```Powershell
> rustup toolchain list
stable-x86_64-pc-windows-msvc (default)
beta-x86_64-pc-windows-msvc
nightly-x86_64-pc-windows-msvc
```

你可以看到，稳定的工具链是默认的。大部分Rust用户在大多数时间里都在使用稳定版本。你在大多数时间里可能也想使用稳定版本，但同时也想在特定的项目里使用nightly版本，看看一些前沿的特性。想要实现这一点，你可以在那个项目的目录下使用`rustup override`来设置在这个目录下的`rustup`所使用的是nightly的工具链：

```bash
$ cd ~/projects/needs-nightly
$ rustup override set nightly
```

现在，每一次在 *～/projects/needs-nightly* 目录下对`rustc`和`cargo`的调用，`rustup`都会确保你使用的是nightly版本，而不是默认的稳定版本。

## RFC流程和团队

那么如何了解新特性的信息呢？Rust的开发模型遵循*征求意见（Request For Comments, RFC）流程*。如果你希望让Rust有某方面的提升，你可以写一个建议，也就是一个RFC。

任何人都可以踢出RFC来让Rust有所提升，这些建议会被Rust团队审查和讨论，其中也包括许多的子团队。Rust的网站上有[团队完整列表](https://www.rust-lang.org/governance)，每一个项目的部分都包括一个团队：语言设计，编译器实现，基础设施，文档等等。最合适的一个团队会阅读提议和评论，并给出他们自己的评论，最终，会达成一个接收或拒绝这个特性的共识。

如果一个特性被接收，那么Rust仓库中会创建一个issue，某个人可以实现它。实现它的人可能并不是最初踢出它的人！当这个实现被准备好后，它会在`master`分支落地，当然和我们前面讨论的一样，它会隐藏在一个特性开关后。

一段时间后，一旦使用nightly版本的Rust的开发者尝试了这些特性，团队成员会讨论这些新特性，以及它在nightly版本中工作的情况，并决定它是否应该加入稳定版本的Rust。如果大家的意见是正向的，那么特性的开关会被移除，这个特性就被认为是稳定的了！它会搭上下一班稳定版本的列车。
